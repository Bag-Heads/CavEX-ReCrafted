# CaveWii_v2 -- lane B briefs B3 (LCE-02) and F3 (gates), 2026-09-14.
# The canonical STATISTIC COUNTER id every Beta block id folds onto, in each
# of Beta 1.7.3's four per-id statistic arrays -- or "-" where Beta has no
# counter for that id in that array AT ALL.  Golden input to
# tests/test_stats_counters.c, which pins stat_canonical_block() and
# stat_alias_block_in() to every one of these 1024 cells.
#
# Format: one line per block id, whitespace separated
#     <id> <mineBlock> <craftItem> <useItem> <breakItem>
# each column being the id of the counter a count for <id> lands on, or "-"
# for "Beta has no counter here at all".  Lines beginning with '#' are
# comments.
#
# ---------------------------------------------------------------- DERIVATION
# Not a snapshot of what the code did before this file existed: every cell is
# computed from the Beta initialisation sequence -- REGISTRATION first, then
# the fold -- and three of them moved the module (see CORRECTIONS).  The
# decompile is McBetaCpp/srcorigjava.
#
# 1. Each array is built by its own registration loop.  All four require a
#    Beta BLOCK at the id: func_25153_a tests `Block.blocksList[j] != null`
#    (StatList.java:86) and the other three test `Item.itemsList[l] != null`
#    (StatList.java:70, 108, 134), which Block.java:863-869 fills with an
#    ItemBlock for exactly the non-null blocks.  Block.<clinit> populates
#    1 (stone) .. 96 (trapdoor) with no gaps (Block.java:759-854), so ids 0
#    and 97..255 are "-" in every column.  On top of that:
#      mineBlock  StatList.func_25153_a  (StatList.java:81-98)
#                 -- DECIDING LINE :86, `... && Block.blocksList[j]
#                    .getEnableStats()`.  The twenty disableStats() blocks
#                    (Block.java:765-854: 7 8 9 10 11 18 26 51 52 55 59 63 64
#                    68 71 83 92 93 94 96) get NO entry, which is why their
#                    column reads "-".
#      craftItem  StatList.func_25157_c  (StatList.java:42-79)
#                 -- DECIDING LINES :50-53 (every CraftingManager recipe
#                    output) and :56-59 (every FurnaceRecipes smelting
#                    output), collected into a HashSet and registered at :75.
#                    Nothing else is registered.
#      useItem    StatList.func_25155_a  (StatList.java:100-124)
#                 -- DECIDING LINE :108, `if(Item.itemsList[l] == null)
#                    continue;` and nothing more: getEnableStats() is NOT
#                    consulted, so a door or a cake has a use counter even
#                    though it has no mine counter.
#      breakItem  StatList.func_25149_b  (StatList.java:126-145)
#                 -- DECIDING LINE :134, `... && Item.itemsList[l]
#                    .isDamagable()`, which is `maxDamage > 0 && !hasSubtypes`
#                    (Item.java:115-118).  Every block item is an ItemBlock
#                    (Block.java:866) or one of ItemCloth/ItemLog/ItemSlab/
#                    ItemSapling/ItemLeaves/ItemPiston, and not one of them
#                    ever sets a maxDamage -- five of them call
#                    setMaxDamage(0) explicitly.  So func_25149_b registers
#                    NOTHING in 0..255 and the whole breakItem column is "-".
#
# 2. Every array then goes through replaceAllSimilarBlocks (StatList.java:
#    147-160), which is these eleven calls, in this order, written (i, j):
#      (9,8) (11,11) (91,86) (62,61) (74,73) (94,93) (76,75) (40,39)
#      (43,44) (2,3) (60,3)
#    and replaceSimilarBlocks (StatList.java:162-176) folds each one by a
#    branch on which SIDE is registered in THAT array:
#      if (a[i] != null && a[j] == null)  a[j] = a[i];   // j takes i's
#      else                               a[i] = a[j];   // i takes j's
#    So the fold direction is a property of the (array, pair), not of the
#    pair -- which is the whole reason this table has four columns.  The rows
#    are applied IN ORDER against the running array: (2,3) can write a[3]
#    before (60,3) reads it.  A row whose two cells are both null leaves both
#    null: a fold never invents a counter.
#
# ---------------------------------------------------------------- CORRECTIONS
# Three cells contradict the flat single-direction table B1/F1 shipped, and
# the module was changed to match this file, not the other way round:
#
#  * water.  The call is `replaceSimilarBlocks(a, Block.waterStill.blockID,
#    Block.waterMoving.blockID)` (StatList.java:149) -- i = STILL (9),
#    j = MOVING (8) -- so 9 folds onto 8.  F1 had (8 -> 9).  Unobservable in
#    mineBlock (both are disableStats), observable in useItem.
#  * jack-o-lantern / pumpkin in craftItem.  `CraftingManager.java:131`
#    outputs Block.pumpkinLantern (91); nothing outputs Block.pumpkin (86).
#    So a[91] != null and a[86] == null, Beta takes the INVERTING branch, and
#    the shared counter is 91 -- the pumpkin row takes the lantern's counter.
#  * redstone torch in craftItem.  `CraftingManager.java:170` outputs
#    Block.torchRedstoneActive (76); nothing outputs the idle 75.  Same
#    branch, shared counter 76.
#  With the registration sets in the module (F3) both inversions now FALL OUT
#  of the same branch every other pair takes; CW_BLOCK_CRAFT_INVERT_ROWS in
#  stats_table.h stays as the cited expectation the tests pin.
#
# A FOURTH correction, this time to B3's own header: the craftItem output list
# below had 38 entries and was missing 67 (cobblestone stairs,
# CraftingManager.java:158).  It has 39.
#
# --------------------------------------------------------- THE GATES (F3)
# B3 recorded the three registration gates here and left them OUT of the
# module; F3 implements them, so they are now IN these columns:
#
#  (a) craftItem exists for 39 block ids -- the recipe/smelting outputs
#      1 5 20 22 23 24 25 27 28 29 33 35 41 42 44 45 46 47 50 53 54 57 58 61
#      65 66 67 69 70 72 76 77 80 82 84 85 89 91 96 -- plus the four an alias
#      row then reaches (86 <- 91, 62 -> 61, 75 <- 76, 43 -> 44).  The other
#      213 rows read "-".  Cited per id in CW_BLOCK_CRAFT_OUTPUT_ROWS.
#  (b) breakItem exists for NO block id at all (the deciding line above), so
#      the whole column is "-".  A block is not damagable, so no well-formed
#      GE_ITEM_BROKEN can land there.
#  (c) all four arrays need a Beta block at the id, true for 1..96 only.
#      CaveWii registers 97 (tree2d) and 200 (iron chest), which Beta has no
#      block -- and therefore no statistic -- for.  LEAD RULING (F3): a
#      net-new block is outside the Beta table and gets NO statistic in any
#      column; a later card may add CaveWii-owned counter ids on top rather
#      than borrowing Beta's.
#
# Column totals, as a shape check on the whole table: mineBlock 76 counters
# (96 blocks - 20 disableStats), craftItem 43, useItem 96, breakItem 0.
